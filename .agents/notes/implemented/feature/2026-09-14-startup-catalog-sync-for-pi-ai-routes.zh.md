# Agent Note：pi-ai 目录路由的启动时目录同步

状态：已实现

[English](2026-09-14-startup-catalog-sync-for-pi-ai-routes.md) | 中文

## 问题

已安装 pi-ai 目录路由服务的模型列表是编译进 `@earendil-works/pi-ai` npm 包的快照。提供方上线新模型后，服务端仍沿用旧列表，直到 pi-ai 发布新版本：OpenCode Go 网关已经在它的列表端点上线 `deepseek-v4.1-flash`，而固定的 pi-ai 0.85.1 快照仍只包含 V4 家族，任何配置界面都无法显示这个新增。发现功能也帮不上忙：目录路由按设计由已安装注册表直接回答、不发网络请求，而 settings 的 `models` 列表会整体替换目录，把部署手写的答案写进 `settings.yaml`。

## 决策

适配器新增一项选择加入的启动同步。在 `llm-pi-ai` 分节设置 `catalogSyncEnabled: true` 后，每条出现的目录路由会在其自身的列表端点被询问一次、每进程一次——挂载时，或 settings 分节点名它时。合并后的回答（路由可列示协议的并集，每个模型以最先列出的为准并按列出它的协议打标，端点披露容量时采纳容量）原子地写入 `<catalogCacheDir>/<provider>.json`，此后解析以它替代冻结快照。快照也描述的模型保留该条目的元数据，并叠加同步得到的名称与容量，因此只披露 id 的列表也能得到描述完整的模型。自带 `models` 列表或 `modelOverrides` 的路由永不同步；端点失败、拒绝或返回空时保留此前的目录；缺文件或缓存损坏回答为缺失、由快照服务——无论哪种情况路由都保持离线可用。路由全程仍是已安装提供方：`settings.yaml` 不会新增任何内容。

同步是 fire-and-forget，绝不让挂载失败。Models 界面的拉取动作也会按需刷新该路由的缓存，因此会话进行中也能拿到新增模型。

覆盖：缓存文件格式、指纹、原子写入、按 mtime 的 serving 备忘与损坏/缺失回退在 `catalog-cache.spec.ts`；列表并集、协议去重、先列获胜打标、逐端点失败容忍与中止在 `discovery.spec.ts`；缓存优先于快照的解析与 `resolveProfiles` 带目录语义在 `catalog.spec.ts`；另有真实组合测试：从 settings 注册目录路由、挂载时经本地端点同步、服务同步后的列表；另一条在关闭同步时钉住快照。

## 备选方案

- **TTL 后台刷新。** 最初的 fork 特性（在本包对齐上游架构时被移除）每七天或按 pi-ai 指纹变化刷新一次缓存。恢复时否决：部署要求的是"每次启动强制检查一次"，而按计划自动后台拉取比每路由每进程一次的同步检查更难推理。
- **默认开启同步。** 否决：每条已配置目录路由都会在每次挂载时致电其提供方，改变每个现有部署的行为，并会让测试套件触达真实第三方端点。开关默认 `false`，settings 分节一行即可开启。
- **让 discovery 直接在线询问目录路由。** 界面动作存在，但它的回答是草稿元数据；持久化它反正需要同一层缓存，且逐次拉取的遗漏无法在两次动作之间保持路由最新。

## 后果

- 想要上游最新模型列表的部署开启同步，下一次启动即可拿到：在 `llm-pi-ai` 分节设置 `catalogSyncEnabled: true`，可选 `catalogCacheDir`（默认 `$DSH_HOME/llm-pi-ai/catalog-cache`）。
- 缓存服务与同一开关绑定：关闭同步时不访问任何提供方端点、不读取缓存文件，行为与之前逐字节一致。
- 同步列表只披露 id、名称、有时含容量；推理等级、价格与兼容性怪癖仍来自 pi-ai 快照，因此全新模型以路由默认容量出现即可服务，直到 pi-ai 追上来（之后指纹不匹配会让针对旧快照的缓存失效）。
- 同步端点使用路由的有效端点（profile 覆盖了 `baseURL`/`api` 时用配置值），而非冻结目录的地址——询问的是代理或自托管副本，而不是厂商端点。
