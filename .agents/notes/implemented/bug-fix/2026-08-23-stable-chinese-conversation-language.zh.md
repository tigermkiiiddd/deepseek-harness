# Agent Note: 保持默认对话语言稳定

Status: implemented

[English](2026-08-23-stable-chinese-conversation-language.md) | 中文

## 问题

随附 persona 要求模型跟随用户语言并在用户切换时切换，却没有定义哪些消息可以作为依据。随着对话增长，英语的系统段落、工具说明与结果、代码、日志、subagent 报告以及助手先前的回复可能压过用户的中文消息。`minimal` preset 则完全没有语言策略。压缩（compaction）会放大同一歧义，因为英语检查点会作为合成的 user 消息进入持久对话前缀。

## 决策

`standard`、`code` 与 `cordis` agent persona、`minimal` 完整 persona，以及 Web 与 headless 部署 persona 都默认让所有面向用户的沟通使用简体中文。只有用户亲自提出的明确语言要求会改变该默认值。系统或开发者文本、生成的摘要与检查点、工具输出、代码、日志、文件或引用内容、subagent 消息、助手先前的回复以及简短确认都不会改变语言。代码、标识符、路径、命令、错误原文、专有名词及用户明确指定语言的交付物保留任务所需的语言。

该规则保留在每个既有 persona 内。组合不会新增独立的尾部提示词段落，也不会注入重复的 runtime-context 提醒。带作用域 persona 仍会遮蔽部署 persona；`minimal` 则把规则嵌入自身的 `complete: true` 文本，因为完整提示词会抑制所有配套段落。

两套随附压缩摘要器都遵循当前系统提示词的对话语言策略与用户明确偏好，并将所得语言记录在 `Critical Context` 下。只有两者都未确立语言时，才回退到用户最近一条实质性自然语言请求。摘要器保留精确的技术字面量与既有英语 Markdown 标题。尾随指令仍是逐字匹配的已路由请求前缀之后唯一的新输入，因此提供方的前缀 KV Cache 复用保持不变。

## 考虑过的替代方案

- **继续跟随对话呈现出的语言**——不采纳，因为在许多长时间 coding 会话中，生成内容与技术内容的英语会占据主导，但这不代表用户作出了选择。
- **在每次组装的提示词末尾追加独立语言策略段落**——不采纳，因为这会把同一策略作为独立提示词贡献反复加入、增加噪音，而且不增加例外就无法越过 `complete: true` persona。
- **让所有压缩检查点保持英语**——尽管这样能统一工程文体，仍不采纳，因为检查点会作为合成的 user 消息交付，并可能把后续面向用户的回复带成英语。无需规范化叙述语言，也能保护精确的技术字面量。
- **验证并重新生成非中文 assistant 输出**——不采纳，因为额外模型调用会增加延迟和成本，而且输出语言检测器可能错误拒绝有效代码、引用文本或用户要求的外语交付物。

## 后果

- 长对话、工具密集轮次、压缩、恢复与模型切换都会保持简体中文，除非用户明确提出其他要求。
- 用户选择其他语言时，检查点可能把非英语叙述带入原本以英语技术内容为主的前缀；这以放弃单一规范工程文体为代价保留对话意图。
- 固定策略会增加既有 persona 的文本，但不会创建新的提示词段落或动态上下文事件，因此首次请求后渲染前缀保持稳定。
- 真实 Web `minimal` 快照固定完整 persona，随附组合覆盖固定全部带作用域 persona，压缩单元测试与真实循环覆盖固定最终摘要指令。直接摘要调用仍不发出 `assistant/chunk` 事件，因此 transcript 快照无法观察其指令。
