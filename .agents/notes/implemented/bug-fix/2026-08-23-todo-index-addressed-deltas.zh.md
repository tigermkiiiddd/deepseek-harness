# Agent Note: 按索引寻址的 todo 增量

Status: implemented

[English](2026-08-23-todo-index-addressed-deltas.md) | 中文

## 问题

todo 增量更新曾把供人阅读的 `content` 字段作为 upsert 键。模型在汇报进度时经常完善措辞，因此改名后的任务无法命中原条目，反而会作为第二条任务追加。重复数据会持久写入 `todo/write`；UI 客户端只是正确显示了已损坏的列表。

## 决策

`todo_write` 继续在 `todo/write` 中保存完整 `TodoItem[]` 快照，但只接受按索引寻址的变更：必填 action `add` 追加 `todos`，`update` 应用 `updates: [{ index, content?, status? }]`，`remove` 删除 `indices`，`clear` 清空列表。协议既不提供 `merge`，也不提供整表 `replace`：upsert 无法区分有意新增与任务改名，而可用的替换路径会让模型绕过增量并反复传输整张列表。

`update` 永不追加。每个更新和删除索引都指向调用前的列表；索引重复、为负或越界时，调用会失败且不写事件。更新必须修改 `content`、`status`，或同时修改两者。完整结果必须保留唯一且非空的 content，并在追加前满足已配置的活跃任务数量规则。

持久化的 `TodoItem` 仍是 `{ content, status }`。索引是操作地址，而非持久身份，因此事件格式、投影、ACP 映射和 UI 表示均保持不变。

`todo_read` 返回带有从零开始索引的当前有序列表，且不写事件。工具折叠会在最近一次 `turn/start` 处停止，因此新轮次会从 UI 投影的同一个空当前计划状态开始，而不会恢复上一轮的列表。每次成功的 `todo_write` 结果也会在状态计数后渲染完整的索引结果。因此模型能够在压缩后重新同步，并始终收到最近一次变更产生的索引映射；`todo/write` 本身仍是只供日志与 UI 使用的状态。

## 验证

包测试覆盖：通过 `update` 改名且列表长度不增加、局部字段更新、新增、按调用前索引删除、无效及重复索引、结果内容重复、活跃数量校验、必填 action、拒绝 `replace`、索引渲染，以及在下一次 `turn/start` 重置。完整 agent loop 测试通过真实工具注册表发送索引更新，并验证 `todo_read` 返回当前索引映射且不追加另一条 `todo/write`。

## 曾考虑的替代方案

**继续按 `content` 匹配。** 再强的指令也无法把可编辑的展示文字变成稳定键。精确匹配会在标点或措辞变化时重现缺陷；模糊匹配则可能不可预测地合并不同任务。

**持久化稳定任务 id。** 这种方式提供独立于顺序的身份，更适合并发的多所有者列表，但会改变 `TodoItem`、每个持久事件和全部消费方。当前列表由单一会话所有且有序，因此位置变更可以在不扩大持久格式的情况下解决已观测缺陷。

**恢复仅整表替换。** 整表替换不需要身份，但会恢复促使增量动作出现的 token 成本和遗漏风险。

**把 `replace` 保留为异常逃生口。** 工具描述未能约束其用途：模型会在普通状态和文字修改中反复选择排在首位的默认动作。移除该动作后才能强制增量传输；完整重排使用显式 `clear`，随后调用 `add`。

## 后果

任务文字可以原地修改而不产生第二个条目，无效目标会失败，不会变成隐式新增。`add` 和 `update` 表达不同意图，协议也无法静默回退到整表写入。索引结果的 token 成本随当前任务数量增长，完整重排需要两次调用（先 `clear`，再 `add`）。由于索引跟随顺序，模型会在 `add` 或 `remove` 后使用最新渲染列表，并在压缩隐藏列表时调用 `todo_read`；如果列表将来出现并发写入方，稳定 id 仍是后续升级路径。
