# Agent Note：JSONL 追加尾部校验抵御并发外部写者

Status: implemented

[English](2026-08-16-jsonl-append-tail-guard.md) | 中文

## 问题

共享同一个 `DSH_HOME` 的两个 dsh 主进程可以同时持有同一会话的活跃实例——例如一个遗留的 `dsh web` 服务和一个新启动的、恢复了同一对话的服务。协调器的恢复互斥是进程内的，而 JSONL 后端追加时没有任何跨进程校验，于是两个进程各自维护自己的序号计数器，把帧交错写进同一个文件。结果是日志中段的 seq 发生回退；读取端的连续性不变式随后拒绝整份日志，Web UI 对该会话显示「历史加载失败」。

## 决策

`dsh-session-persistence-jsonl` 现在跟踪本进程上次离开每份日志时的字节偏移（`expectedTails`，按路径索引），在读取（`readPrefix`）、`materialize`、`repair` 和每次成功追加时记录。`appendLines` 在写入前对文件取 stat——回滚路径本来就有这次 stat——当磁盘上的大小与记录不符时大声拒绝：并发外部写者动过这份日志，追加会把两代序号交错进一份不可读的日志。拒绝之后，重新观察日志（一次新的加载）会重新武装追加器。后端实例从未观察过的路径保留历史上不受检查的首次追加；协调器总是先加载再写入，所以活跃写者一定持有新鲜的记录。

该校验是乐观并发控制，不是锁：stat 与追加是两个独立操作。它能确定性地拦住间隔数秒的写者——也就是实际观察到的故障形态——而 stat 与写入之间残留的微秒级竞态仍然存在。

## 备选方案

**在会话存活期内持有操作系统级文件锁（LockFileEx / flock）。** 暂不采用：它会改变每个平台上的拆卸语义（被杀掉的进程不能把会话锁死给别人），而且乐观校验已经能确定性覆盖的场景不该扩大基于 koffi 的原生接口面。

**在 `DSH_HOME` 上加主级单实例锁。** 否决：不同 profile（CLI、headless、web）合法共享同一个 home；损坏需要同一会话在两个进程中同时活跃，按日志的尾部校验恰好精确对准这一点。

**放任过期写者继续写、读取时再修复。** 否决：交错的两条流是同一轮次的平行历史，无法机械合并；拒绝写入才能保证每份日志可读。

## 后果

恢复会话的第二个进程仍然成功；被抛弃的第一个进程现在会在下一次落盘时收到一个描述性错误，而不是静默写坏文件，写回层会保留并重试该批次（在那里重新加载会话之前会一直失败）。读取和单写者追加不受影响。单元覆盖钉住了跨实例拒绝、拒绝后日志仍然有效、通过重新加载恢复追加能力，以及未观察日志的免检查首次追加。
